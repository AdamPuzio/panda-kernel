# @panda/kernel — Decision Log

Dated, append-only records of decisions made and reconsidered (or deliberately not reconsidered). Per `panda-opencode/working-pattern.md`: when the urge to revisit something already decided shows up, the response is "check here for why not," not "change it." Add a new entry each time a real decision gets made; don't edit past entries except to link a later entry that supersedes one.

## 2026-09-25 — Reviewed `@panda/atom` (from `_delete/panda/playground/atom2/`); not adopted

**Context:** While reviewing legacy/uncommitted work recovered from another machine, found `@panda/atom` — a prior attempt (more recent than the 0.7-era `Entity`/`Hub` system, predating this session's kernel design) at solving the same underlying goals: one base class usable flexibly in many contexts, with built-in tracing/observability.

**How it worked:** Every `Atom` instance auto-scans its own properties at construction time for `$`-prefixed fields that look like other Atom instances (duck-typed via `hasOwnProperty('$props')`), and automatically wires them via a `$infuse()` call — e.g. `$logger = Logger.$infuse({ level: 'debug' })` as a class field gets auto-detected and connected by the base class. Tracing (`Trace`, in `inc/trace.ts`) was hardcoded directly into the shared `Props` base class every Atom uses — one fixed implementation, not swappable.

**Decision: not adopted, for two specific reasons:**

1. **It's imperative-code-first, not JSON-first.** Composition happens by writing a TypeScript class with special property-naming conventions and relying on reflection to wire things at construction time. This is a different mechanism than — not an earlier version of — the kernel's manifest-driven approach (a JSON file describes the composition; a registry resolves it). Given the explicit goal of this whole design effort ("bind everything via JSON, no customizing individual pieces"), Atom's approach doesn't serve that goal; the kernel's does. Adopting Atom's pattern would be a regression relative to what was actually asked for.
2. **Ambient tracing was hardcoded, not pluggable** — every Atom gets exactly one tracing implementation baked into its base class, with no way to swap it. This is the precise anti-pattern the kernel's `registerService`/declaration-merging design (see decision below, and `HANDLERS.md`) was built specifically to avoid. On this axis, the kernel design is a direct improvement over Atom, not a parallel alternative.

**What's worth keeping, noted but not acted on:** Atom's `infuseLevel`/`infusedTo`/`infusedKey` bookkeeping — each instance tracking what it was wired into and at what depth — is a reasonable idea for debugging provenance. Could inform a future addition to `ctx.refs` metadata (recording which manifest key + depth an instance was resolved under). Not built now; revisit only if a concrete debugging need for this surfaces.

**Do not re-litigate this without a specific new reason** — e.g., if a future need arises for code-first (non-manifest) composition as a deliberate escape hatch alongside the manifest system, that's a legitimate reason to revisit; "I liked how Atom felt" is not.

## 2026-09-25 — Added `configure(ctx)` as an optional entity lifecycle hook, ahead of `run(ctx)`

**Context:** Implementing `panda:module` for real (not just on paper) surfaced a genuine gap the design docs hadn't anticipated: a dependent entity's `uses`/`contributesTo` reference to a module's export needs that export to already exist *during the same resolve() pass that wires the dependent* — well before anyone's `run()` is ever called. But the original entity contract only had one lifecycle method, `run(ctx)`, which is wired up but never invoked during `resolve()` itself. `panda:module` had no correct place to eagerly, asynchronously resolve its nested manifest and populate its exports.

**Decision:** added an optional `configure?(ctx): Promise<void>` to `PandaEntityInstance`. The resolver calls it (if present) immediately after construction and *before* applying any link handler for that entity — so by the time anything else's `uses`/`contributesTo` runs, this entity's eager setup is guaranteed complete. Most entities don't need it and simply omit it; `panda:module` is the first (and so far only) entity type that does.

**Why this is a decision worth logging, not just a code change:** it modifies the core entity contract every `@panda/*` package will eventually need to satisfy — worth being able to point back to *why* a second lifecycle method exists rather than having it look like an arbitrary addition later, and worth remembering that "configure declaratively, then execute" (the two-phase language already used for Actions in `SPEC.md`) turned out to need a third phase in between (eager async setup) once module composition was actually implemented.

**Do not re-litigate without a specific new reason** — e.g., if a *third* distinct lifecycle need turns up (this is plausible; `configure()` itself was only discovered by building something real, not by more design), that's a legitimate reason to revisit the shape of the lifecycle, not a reason to add a fourth ad hoc method reactively.

## 2026-09-25 — Adapter pattern confirmed for wrapping real, unmodified libraries; adapters live alongside the library, not inside it

**Context:** Adam's explicit operating principle: libraries in the Panda ecosystem must remain fully usable by a developer who has never heard of a manifest — `new Command({...})` with real functions works exactly as it always did — while ALSO being usable as a manifest-driven entity. Tested this against the real `legacy/panda-command` library via a wrapper entity (`examples/adapters/real-command-entity.ts`) that bridges its function-based `action`/type-constructor config fields to the kernel's named-reference conventions, without touching the library's own source at all (only its `node_modules` were installed, which changes no source file).

**Decision: the adapter pattern works, and lives as a separate file alongside the library, never inside it.** Confirmed by successfully running the real `command-line-args` parsing engine (including short-alias resolution) through the bridge, with zero modifications to `legacy/panda-command`. The adapter imports the library's *built* `dist/` output, not its raw source — this is both more correct (matches how a real consumer would depend on it) and avoids a real, mechanical problem: type-checking raw legacy TypeScript source under the kernel's strict `tsconfig` produced dozens of unrelated errors from code that was never written to satisfy strict mode.

**A concrete bug this exercise caught, worth remembering as a category of risk, not just a one-off fix:** naively re-serializing a subset of config fields (to materialize JSON-safe markers like `type: "String"` into real constructors) accidentally introduced new keys with `undefined` values for fields the original manifest never mentioned at all — which silently overwrote the real library's own default values during its own initialization logic. The fix (only touch a field if it was actually present) is specific to this adapter, but the *category* — "wrapping code you don't own by rebuilding its config object can silently reintroduce fields that were never there" — is worth remembering for any future adapter.

**Do not re-litigate the adapter-lives-alongside-the-library placement decision without a specific new reason** — e.g., if this pattern is repeated for several more libraries and the boilerplate becomes worth extracting into a shared helper, that's a legitimate reason to revisit *where* adapter code lives (a dedicated `@panda/adapters` package, an optional secondary entry point shipped by the library itself, etc.) — not a reason to fold adapter logic into the libraries themselves or into `@panda/kernel` core.

## 2026-09-28 — Phase 2 retrofits (colors, trace, logger, task): widened `PandaStyler`; accepted a known tsc noise trade-off for `@panda/task`

**`PandaStyler` widened.** Wrapping the real `@panda/colors` surfaced that the original ambient contract (`(text: string) => string`) couldn't carry any real styling capability at all — there was nowhere to pass which style to apply. Widened to `(text: string, styles?: string | string[]) => string`, deliberately generic (not typed against `@panda/colors`' specific naming), so kernel core stays uncoupled from any one styling backend. The adapter (`examples/adapters/real-colors-service.ts`) maps this onto `Colors.render(str, styles)`; the full chainable/proxy API `@panda/colors` also offers is a known, deliberate gap in what's reachable through the ambient service — anyone needing it imports `@panda/colors` directly.

**Two real, non-hypothetical findings from wrapping `@panda/trace`, both about its actual runtime behavior:**
1. Its config is computed once, at module-import time. Setting `process.env.TRACE` from inside the same file — even textually before the `import` statements — does nothing, because ES module imports are hoisted above all other top-level code and evaluate first regardless of source order. `TRACE` has to be a real environment variable set before the process starts.
2. `TRACE=on` alone does not enable `trace`-level output. `on` only sets `cfg.on = true`; the severity threshold stays at its default (`info`), and `trace` is always a lower-priority level than `info` — so it's silently blocked unless the level name itself (`TRACE=trace`) is part of the value.

Both are documented directly in `examples/adapters/demo-real-trace.ts`'s comments, since they're real library behavior worth knowing, not adapter bugs.

**`@panda/task`: accepted `tsc` noise as a known, out-of-scope trade-off, not a bug to fix.** `@panda/task`'s own built `dist` bundle is not self-contained — its barrel (`src/index.ts`) eagerly re-exports the built-in `file:create`/`npm:install`/etc. task types, which import `@panda/factory`, which still doesn't exist as a real, resolvable package anywhere in this workspace (the long-standing gap tracked since the original ecosystem analysis). Importing the built `dist` throws `Cannot find module '@panda/factory'` immediately. Worked around by importing the base `Task` class directly from `src/task.ts` (which has no such dependency), bypassing the broken barrel entirely — but that file wasn't written against strict TypeScript, so `npx tsc --noEmit` on `@panda/kernel` now shows real, pre-existing type errors attributed to `legacy/panda-task/src/task.ts` once `real-task-entity.ts` is included. **Decision: accept this, documented clearly in the adapter's own file comments, rather than either modifying legacy source (against the standing "never touch legacy source" principle) or blocking this retrofit on fixing `@panda/factory`** (a separate, larger piece of work — recovering the real implementation found in the `_delete` archaeology folder — that deserves its own deliberate pass, not one silently bundled into a task-runner retrofit). Real runtime behavior was verified directly instead (`examples/adapters/demo-real-task.ts` shows actual `listr2` rendering output), which is what actually matters.

**Do not re-litigate the `@panda/factory` deferral without a specific new reason** — e.g., if a future retrofit needs one of `@panda/task`'s built-in task types specifically (`file:create`, `npm:install`), that's the trigger to finally do the Factory recovery properly, not a reason to patch around it a second time.

**Context:** exactly the trigger named in the previous entry — this session moved on to actually recovering `@panda/factory`, closing the deferral rather than patching around it again.

**What was recovered:** a complete, functioning `PandaFactory` implementation was found in `_delete/panda/@panda/task/@panda/factory/` (from the earlier cross-machine archaeology) — Handlebars-based templating with case-conversion helpers (`kebabCase`, `pascalCase`, etc.), file read/write with `ifExists`/`ifNotExists` policies, JSON read/write, glob-based `list()`, `runCommand()`/`openBrowser()`, plus a ~350-line `virtual-directory.ts` module also exported from its `index.ts`. Copied wholesale into `legacy/panda-factory` (previously an empty stub directory with no `package.json` at all) — not rewritten, not cherry-picked.

**Wiring:** added `legacy/panda-factory` to the root npm workspace; corrected `legacy/panda-task/package.json`'s dangling `"@panda/factory": "file:../@panda/factory"` (a path that resolved to nowhere real) to a normal workspace dependency (`"@panda/factory": "*"`). This is a real edit to `legacy/panda-task`'s source — flagged explicitly as such, distinct from adapter-wrapping, since it's a dependency-declaration correction rather than a behavioral rewrite. Built both packages (`npm run build` in each); `@panda/task`'s rebuilt `dist` dropped from needing a nonexistent module to a normal ~25KB bundle correctly treating `@panda/factory` as an external workspace dependency.

**Verified, standalone, before touching the kernel adapter:** the real `file:create` built-in task type (previously unusable — its own `import { Factory } from '@panda/factory'` threw immediately) now runs end to end — actually writes a file to disk via Factory's real `writeFile()`, confirmed by reading the file back.

**Closed the accepted trade-off from the previous entry:** `examples/adapters/real-task-entity.ts` now imports from `@panda/task`'s built `dist` output, same as every other adapter, instead of reaching around the broken barrel via raw source. `npx tsc --noEmit` on `@panda/kernel` is fully clean again — the `legacy/panda-task/src/task.ts` noise documented in the previous entry is gone, not suppressed.

**Not done as part of this:** `@panda/task`'s built-in task types (`file:create`, `npm:install`, `json:*`, `path:*`) are confirmed working standalone, but `real-task-entity.ts` itself still bridges task steps through named actions rather than exposing those built-in types through its own config shape — a reasonable follow-up, not bundled into this fix.

**Do not re-litigate the workspace-dependency correction without a specific new reason** — it's a one-line fix to a reference that pointed nowhere; there's no meaningful alternative to re-litigate.

## 2026-09-29 — `@panda/scaffold` retrofitted (Phase 2 complete); three genuine, pre-existing bugs found and fixed along the way

**Discovered before writing any adapter code: Scaffold's own `package.json` pinned `@panda/command` at `^0.1.4`, which does not semver-match the `0.2.1` in this workspace.** Confirmed via `npm ls` that it was actually resolving the real, older `0.1.4` from the public npm registry — a genuinely different Command API generation (no `run(argv)` method at all; `init()`/`parse()`/`action()` as separate calls instead). Bumped the range to `"*"` (same fix pattern as `panda-task`'s and `panda-trace`'s dependency corrections) so it resolves the local workspace package instead, then rebuilt.

**That version bump surfaced a real compile-time incompatibility, not just a resolution mismatch:** `@panda/command` had renamed `CommandInterface` → `CommandProps` and `renderHelp()` → `outputHelp()` since Scaffold's source was last touched. Both are small, mechanical, unambiguous fixes (confirmed by reading `@panda/command`'s current source directly) — updated the import and the one call site.

**Two more genuine, pre-existing runtime bugs found only by actually running the retrofit, not by any of the above:**
1. `scaffold.ts`'s `runAction()` calls `actionInstance.when(action, data, factory)` to decide whether to skip an action — but the base `ScaffoldAction` class never defined `when()` at all. Every action execution in this library was already broken (`when is not a function`) before any of this session's changes. Fixed with a minimal default (`async when() { return true }`), matching the base class's existing no-op `run()` pattern.
2. After a successful action, `runAction()` renders a spinner success message via `factory.path(action.successMessage || successMsg || actionInstance.successMessage)` — all three are commonly undefined (no built-in action type's `run()` returns a value, and `successMessage` isn't set by default), making this `factory.path(undefined)` → `Handlebars.compile(undefined)`, which throws unconditionally. This bug hid behind the first one — nobody could have hit it before `when()` was fixed, since execution never reached this far. Fixed with the same fallback pattern already used one line above for `startMessage` (`|| actionType`).

**Verification standard, matching every other adapter this session:** confirmed the actual generated file exists on disk with the correct real-Handlebars-rendered content (`Hello, World!`, using a value that flowed from a real, CLI-parsed `--name World` argument, through the real `command-line-args` engine Scaffold inherits from Command) — not just "no exception was thrown." Also verified the `custom` action type (which embeds a raw `run` function in native usage) bridges correctly through the same named-action-reference pattern as `panda:command`'s `action` field.

**Not fixed, deliberately:** the `custom` action type's `run` field is bridged; per-field `validate` functions on individual scaffold action configs are not (same known limitation as the command adapter). Scaffold's own internal `Factory` class (distinct from the recovered `@panda/factory` package) was left untouched — reconciling the two remains a separate, not-yet-made decision (see `panda-opencode/gaps-and-questions.md`).

**Do not re-litigate the version bump or either bug fix without a specific new reason** — the version bump aligns Scaffold with the same canonical Command every other retrofit uses; both bug fixes are minimal, evidence-based, and match existing patterns already present in the same file.

## 2026-09-30 — `panda:express` — first real EXTERNAL (non-Panda-authored) library wrapper; `longRunning` added to the entity contract

**Phase 3, first deliverable.** Everything designed on paper in `examples/at-scale/express-integration.md` is now built for real in `examples/adapters/real-express-entity.ts`, importing the actual `express` npm package. Three entity types: `panda:express` (host, owns the real `Express` app), `panda:express-route`, `panda:express-middleware` (both contribute via the existing, unmodified `contributesTo` link handler — no changes needed to the resolver or link-handler layer to make this work, confirming the design held up against a real external library, not just `@panda/*` packages).

**`express` itself was only present as an accidental transitive dependency** of `legacy/panda-docs`'s Docusaurus install (via `webpack-dev-server`), not a real, intentional one anywhere. **First attempt got this wrong**: added `express`/`@types/express` directly to `@panda/kernel`'s own `package.json` (even as a devDependency) — which breaks the precedent every other adapter set. `@panda/command`, `@panda/colors`, `@panda/trace`, `@panda/logger`, `@panda/task`, and `@panda/scaffold` are all *workspace members*, resolved via relative `dist/` imports, so kernel's own manifest never has to declare anything about any of them — this is the same principle behind `PandaStyler` being widened to a generic signature instead of a colors-specific one, and services being pluggable via `registerService` instead of hardcoded: **kernel itself stays uncoupled from any specific implementation it wraps.** Corrected: `express`/`@types/express` moved to the workspace *root*'s `package.json` (`panda-workspace-root`, `"private": true`, never published) instead — purely local dev/demo tooling needed to run the example, exactly as invisible to a real consumer of `@panda/kernel` as any legacy package already is. Kernel's own `package.json` has zero entries for Express, same as it has zero entries for every `@panda/*` package it wraps.

This surfaced a second, real, pre-existing problem: pinning `express@^4.22.3`/`@types/express@^4.17.21` at the root creates a genuine version conflict with `legacy/panda-docs`'s own transitive `@types/connect-history-api-fallback`, which wants `@types/express-serve-static-core@5.1.3` for an unrelated purpose (nothing to do with actually using Express) — `@types/express@4.x` wants `4.19.9`. Not resolvable via `npm dedupe` (they genuinely need different majors of the same types package). Fixed with an explicit return-type annotation on `createRealExpressEntities` (the standard, correct fix for the resulting `TS2742: inferred type cannot be named` error), not a workaround that papers over the conflict.

**Action bridge, same shape as every other adapter:** a route/middleware's `action` config resolves via `registry.resolveAction()` at contribution-apply time. Deliberately thin — the resolved action receives the real `req`/`res`(/`next`) directly and is fully responsible for responding, rather than the adapter inventing its own request/response abstraction on top of Express's. Consistent with every other adapter's bridging philosophy this session.

**The one genuinely new thing, exactly as the design doc predicted and did not hand-wave:** `panda:express`'s `run()` starts a server that keeps running — the first entity type built this session where "run() resolved" means "started successfully," not "finished." Resolved by adding `longRunning?: boolean` to `PandaEntityClass` (types.ts) as a self-declared, optional flag (defaults to one-shot for every existing entity type — no other entity needed to change). No resolver changes were needed beyond this: `resolve()` never awaited `run()` itself in the first place (the caller always chose when to call `run()` on a top-level entity), so the only real gap was this documentation/introspection signal for future tooling (a `paws run`, or `validate()`), not an actual execution-model problem. The process staying alive afterward isn't special kernel behavior — it's the same reason any plain `app.listen(...)` script doesn't exit, an open server handle keeps Node's event loop alive. A `close()` function is exposed on `run()`'s resolved value purely so a demo/test can shut it down cleanly; a real long-running deployment never calls it.

**Verification standard, matching every other adapter:** not just "no exception was thrown" — sent a real HTTP request (`fetch`) at the real running server, confirmed the response came from the actual contributed route handler, and confirmed the contributed middleware genuinely ran first (threaded a flag through it and asserted on it in the response body). Passed cleanly on the first real run — no friction or bugs surfaced this time, worth stating plainly rather than manufacturing drama to match the pattern of prior retrofits; not every real-library integration surfaces a bug, and pretending otherwise would be dishonest.

**Now done, confirmed per the design doc's Part 4 — see the dedicated entry below (2026-09-30, "Express's Part 4 gap closed").**

**Phase 3's second deliverable (a structurally different external library, chosen to be unlike a web framework) is still pending** — see `panda-opencode/roadmap.md`.

## 2026-09-30 — `panda:mongodb` — Phase 3's second deliverable; sharpens what `longRunning` actually means

**Chosen deliberately for a different lifecycle shape than Express**, per the gap named in `STATE.md`'s confidence assessment: Express is a long-running HOST that other entities *contribute into*; `panda:mongodb` is a **stateful resource that other entities `uses`** to get a live handle (`ctx.refs.mongo.getDb()`) — no contributions, no accepting incoming work of its own. Implemented in `examples/adapters/real-mongodb-entity.ts`, importing the real `mongodb` npm driver.

**`longRunning` deliberately NOT set on this entity, and this is a real finding, not an oversight.** `panda:mongodb`'s `run()` genuinely *finishes* — "connect, and be ready" is a completed task, unlike Express's "keep accepting and processing new requests forever," which has no completion point at all. That the underlying TCP connection pool happens to keep Node's event loop alive in the background is a driver/runtime detail, not the same kind of ongoing work `longRunning` was added to describe. Building a second real long-running-*adjacent* entity clarified the flag's actual meaning: it's about whether the entity's own job has a completion point, not whether some background resource happens to stay open afterward.

**A second real finding, specific to the `uses` relationship, that Express's `contributesTo` usage never surfaced:** `uses` wires a dependent to the *instance* at construction time (the resolver's topoSort only orders construction), but does **not** automatically call `run()` on that instance first. `getDb()` throws a clear, deliberate error if called before `mongo.run(ctx)` has established a connection — this is the first demo where getting the run() call order wrong produces a real, informative error, because no previous `uses` dependent ever needed its dependency to have already `run()` before being useful (`panda:cli`'s `ctx.refs` entries, for example, were only ever introspected for their name, never called through a method requiring prior setup). `examples/adapters/demo-real-mongodb.ts` calls `mongo.run(ctx)` before `seedAndQuery.run(ctx)` explicitly, and documents why in its own file comment.

**Infrastructure, handled deliberately, not assumed:** this machine already had a running MongoDB Docker container (`mongo-db`) — reused nothing from it. A fresh, disposable, distinctly-named container (`panda-mongo-demo`, a different port) was created for this demo and torn down again afterward, so the demo neither depends on nor interferes with whatever that pre-existing container was actually for. `mongodb` (the driver) was added as a devDependency of the *workspace root*, not `@panda/kernel`'s own `package.json` — same corrected placement as `express`.

**Verification standard, matching every other adapter:** a real insert followed by a real query against a real, running MongoDB instance — confirmed by checking the actual returned document (including a genuine, driver-generated `ObjectId`), not just "connect() didn't throw." Passed cleanly on the first real run.

**Phase 3 is now fully complete — both deliverables done**, each proving a genuinely different lifecycle shape (long-running host + contributions, vs. stateful resource + `uses`) against a real, unmodified external library.

## 2026-09-30 — `$computed` implemented; a new `PandaContext.instances` field added

**Follows the design in `examples/at-scale/computed-values.md` exactly, including all four "Discoveries" made there on paper.** `ComputedValueResolver` (`src/value-resolvers.ts`), marker `$computed`, value shape `{ from, output }` (e.g. `{ "from": "devServer", "output": "port" }`).

**`resolveConfigValues` (and `PandaValueResolver.resolve`) had to become async** — `$computed` needs to `await` a source entity's `provideValue()`, unlike `$input`, which is trivially synchronous. `panda:module`'s call site (the only existing caller) updated to `await` it.

**`provideValue?(output: string): Promise<unknown>` added to `PandaEntityInstance`** (types.ts) — Option B from the design doc, not Option A: reading a computed value NEVER implicitly triggers `run()`. An entity that wants to expose computed values implements this as a distinct, opt-in method; one that doesn't fails clearly and immediately ("does not support computed values"), rather than something running unexpectedly as a side effect of a config value being read.

**`PandaValueResolver.getDependencies?()` added**, mirroring `PandaLinkHandler.getDependencies()` — and `dependency-graph.ts`'s `getEntityDependencies()` now ALSO recursively scans each entity's `config` tree for value-resolver markers, not just sibling link-handler keywords (Discovery 4). This means `$computed` establishes a real topo-sort dependency (the source entity is constructed first) with no `uses` declaration needed alongside it — matching the design doc's own example exactly, which has no `uses` at all.

**A real, non-obvious gap this surfaced, not anticipated by the design doc:** the design's own worked example deliberately has NO `uses` alongside `$computed`, but `ComputedValueResolver.resolve()` still needs to look up the source entity by name from *somewhere*. `ctx.refs` (populated by `uses`) doesn't contain it, since nothing declared `uses`. Fixed by adding a new field to `PandaContext` itself: `instances: Record<string, PandaEntityInstance>` — the FULL manifest-wide instance map, populated by the resolver for every entity regardless of what it declared, distinct from `refs` (which stays scoped to explicit link-handler relationships). This is the one place "which entities can I reach" isn't opt-in per relationship — a deliberate, minimal exception, not a general loosening of the `uses`/`contributesTo` boundary.

**Confirms, a second time, the caller-responsibility finding `panda:mongodb` first surfaced:** `getDependencies()` only guarantees the source entity is *constructed* before the dependent — nothing automatically calls `run()` on it first. `examples/computed-demo.ts` calls `devServer.run(ctx)` explicitly before `openBrowser.run(ctx)`, and includes a negative test proving `provideValue()` fails clearly (not silently, not by auto-running) if called before `run()` ever happened.

**Resolution timing, exactly as Discovery 3 anticipated:** `$input` (via `panda:module`) resolves eagerly, during `configure()`, because it never depends on anything having run. `$computed` resolves lazily — the CONSUMING entity's own `run()` calls `resolveConfigValues` on its own config, on demand, right before the value is actually needed (`examples/computed-demo.ts`'s `PandaOpenBrowserEntity`). Resolving `$computed` eagerly, the way `$input` is resolved, would be resolving too early — before the source entity could possibly have run.

**Verification standard:** ran the exact `devServer`/`openBrowser` scenario from the design doc end to end (a real picked port flows through `$computed` into the dependent's actual output), plus a negative test confirming `provideValue()` throws rather than silently succeeding or auto-running when called too early. Passed cleanly, no bugs found in the existing mechanism it builds on (`uses`, `contributesTo`, `resolveConfigValues`'s recursive walk) — only the new `PandaContext.instances` gap above was genuinely new.

## 2026-09-30 — Express's Part 4 gap closed: contributing into a `panda:express` instance living inside an imported `panda:module`

**The one thing explicitly left unproven when `panda:express` first shipped** (see this file's earlier `panda:express` entry, and `examples/at-scale/express-integration.md` Part 4): can a consumer contribute a route into an Express app that lives *inside* an imported module, not just a local top-level entity?

**Confirmed: yes, with zero new mechanism needed.** `examples/adapters/demo-express-module-nesting.ts` — a published-module stand-in (`express-module-manifest.json`) bundles its own `panda:express` app plus an internal health route, exporting the app as `"app"`. The consumer (`express-module-consumer-manifest.json`) imports it via `panda:module` and declares its own route with `"contributesTo": "restApiStarter.app"` — the same dotted, one-hop reference syntax `uses` already supported, reaching straight through the module boundary. Neither `resolveEntityRef` (`entity-ref.ts`) nor `ContributesToLinkHandler` (`link-handlers.ts`) were written with modules specifically in mind, and neither needed to be — they were already general enough.

**One mechanism this exercised for the first time, worth naming:** `resolver.ts` rebinds every entity's `run()` to a zero-argument closure over its own already-built `ctx`, from WHICHEVER `resolve()` call actually constructed it — for an entity living inside a module, that's the nested `resolve()` call inside `panda:module`'s own `configure()`, not the consumer's top-level one. `demo-module.ts` already proved this for a one-shot command (`getExport('login').run()`); this demo proves the identical mechanism holds for a long-running host entity too — `getExport('app').run()`, zero arguments, correctly resolves against the server's own nested context.

**Verification standard, matching every other Express/module demo:** real HTTP requests against both routes — the module's own internal `/health` route, and the consumer's `/orders` route contributed across the module boundary — confirming both actually respond correctly, not just that resolution didn't throw.

## 2026-09-30 — Phase 4: real npm package resolution for `panda:module`

**A real design gap had to be resolved first, not just an implementation gap:** nothing had ever decided WHERE a published module's manifest actually lives within an npm package. Established the convention now, in `src/npm-resolution.ts`: a package declares `"panda": { "manifest": "<relative path>" }` in its own `package.json` (defaulting to `panda.manifest.json` at the package root if omitted). This reuses the same `"panda"` package.json field found during the very first ecosystem archaeology (`legacy/panda-scaffold`'s own `"panda": { "module": "scaffold" }` marker) as a namespace for Panda-specific package metadata, rather than inventing an unrelated new convention from scratch.

**`resolveNpmModuleSource(source, fromDir?)`** uses `createRequire(fromDir)` + `require.resolve(\`${source}/package.json\`)` to find a real installed package via Node's own module resolution (defaulting `fromDir` to `process.cwd()`, matching the convention `@panda/paws` already established for resolving file paths), reads its `package.json`, finds the declared (or default) manifest path, and parses it. Returns `undefined` — not a thrown error — when `source` isn't a real installed package at all, so `panda:module`'s `configure()` can cleanly fall through to `registry.registerModuleSource()` for anything that isn't (or isn't yet) real. That stand-in is now an explicit test-double mechanism, not the only path — every existing demo using it (`demo-module.ts`) still passes unchanged, since real resolution correctly finds nothing for a `source` like `"@example/panda-auth"` that was never actually installed, and falls through exactly as designed.

**Distinct, deliberate error behavior when a package IS real but misconfigured:** if `source` resolves to a genuine installed package whose declared (or default) manifest file doesn't exist on disk, this throws a clear, specific error rather than silently falling through to the stand-in — that would hide a real configuration mistake by the module's own author behind a confusing, unrelated "no module source registered" error instead. Verified directly: resolving `"tsup"` (a real installed package with no `panda.manifest.json`) throws the correct, specific message.

**`@panda/example-auth-module`** — a new, real workspace member (`@panda/example-auth-module`, matching the existing `@panda/*` workspace glob, no root config changes needed) created purely to prove this end to end: a real `package.json` with the `panda.manifest` field, a real `panda.manifest.json`, installed as a genuine devDependency of `@panda/kernel` itself. This is NOT the same kind of dependency as `express`/`mongodb` (which live at the workspace root specifically to keep kernel uncoupled from implementations it wraps) — `@panda/example-auth-module` isn't something kernel wraps, it's a test fixture proving kernel's OWN resolution mechanism works, the same relationship a library's test suite has to its own fixtures. Listing it directly in `@panda/kernel/package.json` is correct, not an inconsistency with the earlier Express `devDependency`-placement correction.

**`examples/demo-npm-module-resolution.ts`** — the exact same scenario as `demo-module.ts` (same `loginCommand`/`internalDebugCommand`/`exports`/`inputs` shape), deliberately kept identical so the only variable under test is HOW the module's manifest was found, not a different scenario. Zero calls to `registerModuleSource` anywhere in this file. Verified: a real input flows through to the real resolved package's manifest, encapsulation still holds (the unexported command is still genuinely unreachable), and the whole thing passed cleanly on the first real run.

**`docs/modules.md`'s "What this does NOT do yet" section is now out of date** — updated to reflect Phase 4 is done, with the `panda.manifest` convention documented for real module authors.
